# ข้อเสนอการเปลี่ยนแปลง (Proposal)

## เหตุผล (Why)

ระยะที่ 3 (`rough-spec-phase-3.md`) เน้นกรณีพิเศษและข้อมูล ปัจจุบันอาหารที่ถูกยกเลิกตามคำขอของลูกค้า และอาหารที่พนักงานทิ้งเอง ล้วนจบที่สถานะ `cancelled` โดยไม่มีเหตุผลและไม่มีบันทึกว่าเกิดอะไรขึ้นเมื่อใด จึงวิเคราะห์ไม่ได้ว่าเมนูไหนขายดีหรือมีปัญหา พนักงานยังต้องกดอาหารทีละจาน และแอปต้องอยู่ภายในโควตาฟรีของ Vercel และ Neon

## สิ่งที่เปลี่ยน (What Changes)

- **BREAKING (ข้อมูล)** สถานะ "ถูกนำออก" แยกเป็นสองแบบ: `cancelled` (ลูกค้าขอ พนักงานยืนยัน ใส่หมายเหตุได้ถ้าต้องการ) และ `voided` (พนักงานนำออกเองจาก `pending` หรือ `in_progress` ต้องระบุเหตุผลอย่างน้อย 3 ตัวอักษร) ลูกค้าเห็นทั้งสองแบบเป็น "Cancelled" มีเพียงคอนโซลที่แยกความแตกต่าง
- เมื่อบิลปิด อาหารที่ `served` จะเป็น `finished` หากเคลียร์โต๊ะ อาหารที่ยังเป็น `pending`, `cancel_requested` หรือ `in_progress` จะเป็น `voided` พร้อมเหตุผล "table cleared" ส่วน `cancelled` และ `voided` คงสถานะเดิม
- ทุกการเปลี่ยนสถานะถูกบันทึกพร้อมสถานะเดิม/ใหม่ เวลา ผู้กระทำ (พนักงาน อุปกรณ์ลูกค้า หรือระบบ) และโน้ต (ถ้ามี) การเปลี่ยนแบบกลุ่มใช้เวลาเดียวกัน บันทึกเริ่มตั้งแต่ release นี้ ไม่ย้อนเติมข้อมูลของอาหารก่อนหน้า
- JSON endpoint สองตัวที่ต้องล็อกอินและจำกัดตามสาขา เปิดให้ดูประวัติ: จำนวนต่อเมนูตาม menu item ID (สั่ง, finished, cancelled, voided) และ timeline รายจาน กรองตามช่วงวันที่ได้ (และ menu item ID สำหรับ timeline)
- พนักงานเลือกอาหารหลายจานของ **โต๊ะเดียวกันและสถานะเดียวกัน** ได้ (บนบอร์ด แผงด้านข้าง และรายการการ์ดบนโทรศัพท์ ทุกที่มี "เลือกทั้งหมด") และสั่งการครั้งเดียวกับทุกจาน แบบทั้งหมดหรือไม่มีเลย
- ให้อยู่ในโควตาฟรี: หน้าจออัปเดตทุก 10 วินาทีแทน 5 วินาที (spec กำหนด "ภายใน 15 วินาที" แทน 10) โทรศัพท์ลูกค้าหยุดอัปเดตเมื่อโต๊ะไม่มีบิลเปิดอยู่และตะกร้าของตัวเองว่าง README อธิบายงบโควตาของ Hobby/Neon Free และข้อจำกัดของ Hobby ที่ห้ามใช้เชิงพาณิชย์

### สิ่งที่ไม่ทำ (Non-goals)

- หน้ารายงาน กราฟ รายงานข้ามสาขา หรือการ export (มีแค่ JSON API ทีละสาขา)
- การย้อนเติมประวัติของอาหารที่สร้างก่อน release นี้
- การย้อนการเปลี่ยนสถานะ การแก้เหตุผลภายหลัง หรือการทำแบบกลุ่มข้ามโต๊ะหรือข้ามสถานะ
- การ deploy ขึ้น Vercel (ยังเป็นขั้นตอนของเจ้าของ)

## ความสามารถ (Capabilities)

### ความสามารถใหม่

- `order-history`: บันทึกการเปลี่ยนสถานะของอาหารทุกจาน และ JSON telemetry endpoint แยกตามสาขาที่ใช้บันทึกนี้

### ความสามารถที่แก้ไข

- `order-tracking`: วงจรสถานะเพิ่ม `voided` และ `finished` ฝั่งลูกค้าแสดงสถานะที่ถูกนำออกทั้งสองแบบเป็น "Cancelled" อัปเดตภายใน 15 วินาที และหยุดอัปเดตเมื่อไม่มีอะไรให้แสดง
- `payment`: เงื่อนไขการจ่าย ยอดรวมบิล และการปิด session รองรับ `voided` และ `finished` อัปเดตภายใน 15 วินาที
- `restaurant-console`: ปุ่มเปลี่ยนสถานะ (void พร้อมเหตุผล การตัดสินคำขอยกเลิกพร้อมหมายเหตุ) Mark paid เคลียร์โต๊ะ ใบเสร็จ คอลัมน์บอร์ด จำนวนที่หัวคอลัมน์ แถบโต๊ะ แผงด้านข้าง และการอัปเดตภาพรวม ปรับตามสถานะใหม่ และเพิ่มการเลือกและอัปเดตแบบกลุ่ม

## ผลกระทบ (Impact)

- Schema: enum `item_status` เพิ่ม `voided` และ `finished`; ตารางใหม่ `order_item_events` migration เป็นการเพิ่มอย่างเดียว ไม่แก้ข้อมูลเดิม
- `lib/domain.ts` (สถานะ การกระทำ ยอดรวม), `lib/service.ts` (การเปลี่ยนสถานะรองรับแบบกลุ่มและบันทึก event การปิดบิลตั้งสถานะสุดท้าย และ query สำหรับ telemetry), console API เพิ่ม route สำหรับ batch และ telemetry
- UI คอนโซล (การเลือก กล่องถามเหตุผล/หมายเหตุ ชื่อสถานะใหม่), UI ลูกค้า (การแปลงชื่อสถานะ การหยุด polling), ช่วงเวลา polling ใน `lib/client.ts`
- ขยาย test และ browser walkthrough; README เพิ่มงบโควตาฟรี ไม่มี dependency ใหม่
